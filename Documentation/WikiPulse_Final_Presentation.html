Problem Statement & Core Thesis

When real-world events break—elections, aviation incidents, infrastructure outages, scientific milestones, or public controversies—Wikipedia articles experience immediate surges in edit velocity, contributor diversity, byte churn, or reversion conflict. Yet these signals remain fragmented across raw Server-Sent Events (SSE) streams, multi-week historical archives, pageview telemetry, link graphs, Wikidata spatial claims, and external ML models. WikiPulse unifies all seven sources into a fault-tolerant, explainable real-time and historical knowledge-shift platform.

Explainable Multi-Detector Scoring & Data-Engineered Spark ML Pipeline

65.04% → 9.14% / 0.00% False Alerts · Zero Python UDFs
Detector B · Explainable Score (0–100)
  • 5 Additive Weights: Velocity z (35) + Editor Surge (25) + Byte Churn (20) + Consensus/Dispute (10) + Pageviews (10).
  • Dampening Guardrail: Suppresses bot-only and low-surge routine chatter → cuts false alerts from 65.04% to 9.14%.
  • Exact Audit Parity: Component contributions sum identically to the alert score + ≥2 reasons.
Detector C · Two-Stage pyspark.ml
  • Stage 1 (Unsupervised): VectorAssembler → StandardScaler → KMeans(k=6) (Silhouette 0.5546) → f_centroid_distance.
  • Stage 2 (Supervised): 9D vector (8D + centroid distance) → RandomForestClassifier (40 trees, depth 6).
  • Blended Score: Combines cluster distance + RF probability → 100% precision on 8d eval (817/817).
Data Engineering for ML at Scale
  • Zero Python UDFs: 8D log1p skew transforms & vector_to_array run natively in Catalyst/Tungsten JVM across 1.50M windows.
  • DAG Caching: km_scored.cache() materializes Stage-1 distances once, avoiding redundant scans during RF training & scoring.
  • Idempotent Serving: Deterministic SHA-256 alert_id + Spark 75.4% pre-filter before Lift Wing inference.

11 · Statistical Foundation · Historical Baselines

Scalable Zero-Inclusive Baselines & Session-Aware Normalization

3,307,257 Pages · 47-Day Clean Baseline Window
1. Sparse Zero-Inclusive Activity Profiling

Measuring normal activity using only active hours inflates baselines on rarely edited pages—which make up over 92% of Wikipedia. At the same time, generating a row for every page and every hour across 47 days would explode to 3.73 billion rows.

  • Single-Pass Sparse Aggregation: Spark aggregates only observed active hours per page while accounting for every quiet hour across the full 47-day calendar window—delivering exact baseline averages and spread at a fraction of the memory cost.
  • Stability Guardrail: A minimum variability floor prevents dormant pages from producing noisy scores while preserving crisp sensitivity when genuine news breaks.
2. Burst-Aware Editor Scaling & Conflict Separation

Human Wikipedia edits arrive in concentrated collaborative sessions rather than evenly spaced ticks throughout the day. Dividing daily editor counts uniformly across short windows triggers constant false alarms during ordinary editing bursts.

  • Session-Clustered Expectations: Expected contributor counts for 5-minute and 1-hour windows are calibrated to realistic editing bursts rather than uniform clock slices.
  • Leakage-Free & Conflict-Aware: Baselines are frozen strictly prior to evaluation days and track constructive net growth separately from back-and-forth rewriting volume.

How WikiPulse Solved Wikipedia's Fixed-Threshold Problem

65.04% → 9.14% / 0.00% False-Alert Reduction
Why Naive Fixed Thresholds Failed
  • Chronic False Positives (65.04% False Alerts): Hyperactive list pages (Deaths in 2026: 71.3 ed/day) and destructive revert wars cross static rules every hour.
  • Missed Quiet-Page Shifts: 92.31% of Wikipedia receives < 0.2 ed/day; sudden 5-edit quiet-page surges and 2-editor major rewrites slip right under static cutoffs.
How WikiPulse Solved Both Failure Modes
  • Normalized Every Page Against Itself: 47-day zero-inclusive baselines + session-aware editor scaling adapt cleanly across all 4 activity tiers (3.31M pages).
  • Multi-Signal & Spark ML Disambiguation: Rewriting-volume separation, ≥2.5× pageview confirmation, and two-stage pyspark.ml cut false alerts to 9.14% / 0.00%.
