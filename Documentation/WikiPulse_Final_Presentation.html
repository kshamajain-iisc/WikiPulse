Project Introduction, Distributed Thesis & Headline Telemetry

67 Days · 2026-09-15 to 2026-11-20
Core Problem & Distributed Systems Thesis

When real-world events occur—elections, aviation incidents, infrastructure outages, scientific breakthroughs, or public controversies—Wikipedia articles experience immediate surges in edit velocity, contributor diversity, byte churn, or reversion conflict. However, these signals are fragmented across raw Server-Sent Events (SSE) streams, multi-week historical archives, Analytics pageview APIs, MediaWiki link graphs, Wikidata spatial claims, and Lift Wing ML models. WikiPulse unifies these seven sources into an explainable, fault-tolerant real-time and historical intelligence platform.

Production Technology Stack & Design Choices
  • Streaming Broker & Replay: Apache Kafka 3.9.1 (ZooKeeper-free KRaft mode, acks=all, idempotent Snappy producer) + SSE Collector (Last-Event-ID cursor) + 1x..100x Replay Producer.
  • Distributed Compute (pyspark.sql.DataFrame): Apache Spark 4.2.0 Catalyst SQL DataFrames & Structured Streaming (10m event-time watermark + stateful dedup) power 100% of production data preparation; low-level Python RDDs are used strictly in Experiment #3 for engine benchmarking (2.03x–2.86x DataFrame speedup).
  • Machine Learning (pyspark.ml): DataFrame-based Spark ML pipeline (VectorAssembler → StandardScaler → KMeans k=6 → RandomForestClassifier 40 trees) + Wikimedia Lift Wing Revert Risk API.
  • Lakehouse & Serving UI: 11 Partitioned Snappy Parquet tables + PyArrow 26.0 zero-copy reader + 8-screen Dash 4.5 & Plotly 7.1 web suite (< 1.35s query latency).

02 · Problem Definition & Motivation

Why Naive Fixed Thresholds Fail on Wikipedia

4-Order-of-Magnitude Baseline Skew
Failure Mode 1: Chronic False Positives (65.04% False-Alert Rate)
  • Hyperactive list & season pages (Deaths in 2026: 71.3 ed/day, 149k views/day; India at the 2026 Asian Games: 41.3 ed/day) cross static rules every hour during routine maintenance.
  • Static rules treat destructive revert wars (e.g., 26 reverts in 1 hour with flat net growth) identically to constructive breaking news.
Failure Mode 2: Missed Quiet-Page Shifts (60.0% Synthetic Recall)
  • 92.31% of Wikipedia pages receive < 0.2 edits/day (dormant baseline).
  • When a real-world event triggers 5 collaborative human edits in 5m on a specialized page ($z = +49.9$) or a 2-editor +38.7 KB major rewrite, static rules miss it completely.

How WikiPulse Solves Both Failure Modes

1. Zero-Inclusive Per-Page Baselines ($\mu, \sigma$ across 1,128 UTC hours)  ·  2. Session-Clustered Window Scaling ($1/18$ daily editors for 5m, $1/6$ for 1h)  ·  3. Rewriting Volume Decomposition ($\sum|\Delta| - |\sum\Delta|$)  ·  4. Pageview Corroboration Guardrail ($\ge 2.5\times$ baseline views required for CONFIRMED_NEWS)

06 · Zero-Inclusive Baselines & Knowledge Churn Intelligence

Zero-Inclusive Moments & 5.83 GB Rewriting Volume Decomposition

60.21% of Wikipedia Byte Movement Is Rewriting / Conflict
1. Zero-Inclusive Sufficient Statistics (47d, $H = 1,128$ Hours)

Averaging only over active hours overestimates baseline velocity on quiet pages. WikiPulse computes exact zero-inclusive population moments from sparse active sums across all $H = 1,128$ hours:

μ_hour = (Σ x_h) / 1128   |   σ_hour = √max(σ_min², (Σ x_h²)/1128 - μ_hour²)
  • Session-Clustered Editor Scaling: Expects $\max(0.20, \mu_{\text{daily\_editors}}/18)$ editors per 5m window and $\max(0.35, \mu_{\text{daily\_editors}}/6)$ per 1h window.
  • 2,000-Event Manual Audit (Exp #1): 100% exact byte match (gross = 2,024,277 B, net = +845,023 B, rewriting = 1,179,254 B).

07 · Anomaly Detection & Spark ML (pyspark.ml) Pipeline

Three-Paradigm Scoring & Two-Stage Hybrid Spark ML Architecture

Explainability + 100% ML Precision
Detector A · Fixed Threshold Rule
  • 5m Rule: Mainspace (ns=0) with $\ge 6$ human edits & $\ge 3$ distinct human editors.
  • 1h Rule: Mainspace with $\ge 15$ human edits & $\ge 4$ distinct human editors.
  • Weakness: Blind to page baseline ($\mu, \sigma$), revert ratio, and pageview corroboration.
Detector B · Explainable Historical Score (0–100)
  • 5 Additive Components: Velocity $z$-score (35) + Editor Surge (25) + Byte Churn (20) + Consensus/Dispute (10) + Pageviews (10).
  • Dampening ($w_{\text{damp}}$): $0$ on bot-only; $0.55$ when $z_{\text{vel}} < 2.5$.
  • Exact Additive Parity: $\sum \text{feature\_contributions} \equiv \text{historical\_score}$ + $\ge 2$ reasons (avg 4.03).
Detector C · Two-Stage Spark ML (pyspark.ml)
  • Stage 1 (KMeans k=6): 8D features → StandardScaler → KMeans(k=6) (Silhouette = 0.5546) → Euclidean distance $d_{\text{centroid}}$.
  • Stage 2 (RandomForest 40 Trees): 8D + f_centroid_distance (9D) → blended $0.45 S_{\text{kmeans}} + 0.55 S_{\text{RF}}$.
