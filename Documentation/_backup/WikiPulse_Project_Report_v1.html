1. Problem: Definition, Motivation, Design Goals, Features Required, Scalability/Performance Goals

1.1 Problem Definition

Wikipedia functions as a living global knowledge base where external real-world events—national elections, aviation accidents, infrastructure outages, scientific breakthroughs, and public controversies—trigger immediate, acute shifts in collaborative editing behavior. Within seconds of an event, affected articles experience sudden edit velocity spikes, rapid arrivals of distinct human contributors, structural text additions, or intense back-and-forth reversion disputes. However, these behavioral signals are highly fragmented across separate Wikimedia interfaces: (1) real-time Wikimedia EventStreams Server-Sent Events (SSE) feeds emit raw edit notifications without historical baseline context or reader traffic; (2) longitudinal baseline behavior requires multi-week MediaWiki Action API historical archives and daily Wikimedia Analytics REST API metrics; (3) topic spillover across related pages is embedded in 1-hop MediaWiki outgoing link and incoming backlink graphs; and (4) vandalism risk, textual changes, and physical event coordinates require revision comparison diffs (action=compare), Wikidata spatial claims (wbgetentities), and Wikimedia Lift Wing ML inference.

Because these signals are isolated across disparate APIs and latencies, distinguishing genuine breaking knowledge shifts from routine maintenance, automated bot sweeps, or destructive edit wars in real time is a challenging distributed data engineering problem. WikiPulse solves this by unifying live streaming and historical batch processing into a fault-tolerant platform that benchmarks live activity against zero-inclusive per-page baselines, classifies anomalies via explainable scoring and Spark ML (pyspark.ml), and contextualizes shifts with link spillover graphs, sanitized diffs, privacy-preserving subject maps, and calibrated Revert Risk scores.

1.2 Motivation: Why Fixed Thresholds Fail on Wikipedia

As identified in our proposal, naive static rules such as "15 edits in five minutes" (or "≥ 6 human edits in 5 minutes") fail fundamentally in two opposite directions because baseline editing activity across English Wikipedia spans more than four orders of magnitude:

Activity Tier Daily Edit Threshold All Profiled Pages (3,307,257) Mainspace ns=0 (2,306,368) Representative Pages & Anomaly Detection Consequence
quiet < 0.2 edits/day 3,052,962 (92.31%) 2,118,330 (91.85%) Regional/biographical pages · 4–5 collaborative edits in 5m = massive shift (z > +40) missed by fixed rules.
moderate 0.2 ≤ μ < 2.0 ed/d 217,225 (6.57%) 165,675 (7.18%) Standard encyclopedic articles · Requires per-page zero-inclusive (μ, σ) normalization.
active 2.0 ≤ μ < 15.0 ed/d 34,298 (1.04%) 20,835 (0.90%) Ongoing news topics · Requires contributor surge ratio and daily pageview corroboration.
hyperactive ≥ 15.0 edits/day 2,772 (0.084%) 1,528 (0.066%) Deaths in 2026 (71.3 ed/d, 149k views/d), Western painting (62.1 ed/d) · Crosses fixed rules every hour.
  • Failure Mode 1 — Chronic False Positives on Hyperactive Articles (65.04% False-Alert Rate): Hyperactive list and seasonal pages (e.g., Deaths in 2026 with 3,357 baseline edits, India at the 2026 Asian Games with 1,944 edits, Confectionery store with 29.48% baseline revert ratio) exceed static edit counts during routine hourly maintenance, while fixed rules also misclassify destructive revert wars (flat net growth) as breaking news.
  • Failure Mode 2 — Missed Shifts on Quiet Articles (60.0% Recall on Controlled Shifts): Because 92.31% of Wikipedia pages receive < 0.2 edits/day, a sudden cluster of 5 collaborative human edits in 5m on a quiet page—or a 2-editor +38.7 KB major rewrite—is missed completely by static count rules.

WikiPulse was designed around six core architectural goals and five required analytical features from our project proposal:

1.4 Scalability, Performance & Feature Evaluation Goals

Our proposal defined 14 quantitative success criteria: 6 Scalability/Performance Goals—(P1) ≥ 99% valid event retention in raw storage; (P2) 0 duplicate alerts after restart/replay; (P3) closed 5-minute window latency < 60s under load; (P4) processing rate ≥ input rate during normal operation and backlog draining to 0 after restart; (P5) runtime, shuffle, memory, and storage reported for all scale experiments; (P6) stored Parquet dashboard queries executing in < 2.0s—and 8 Feature Quality Goals—(F1) 100% recall on injected shift patterns with ≥ 2 reasons; (F2) lower false-alert rate for historical score vs. fixed threshold in a reviewed sample; (F3) ≥ 90% usable revision diffs; (F4) ≥ 95% usable Revert Risk scores with offline fallback; (F5) empirical risk threshold calibration against actual 48h reverts; (F6) 100% map points tagged with source/quality while preserving unlocated alerts; (F7) exact match between Spark churn totals and manual sample totals; and (F8) explicit source last_available_date and missing-data indicators on historical views.

2.2 Data Volume, Ingestion Hygiene & Canonical Shared Data Model

Across our continuous 67-day English Wikipedia collection (2026-09-15 to 2026-11-20), WikiPulse collected 21,454,187 raw events in 1,456.93 MB of .jsonl.gz (~9.60 GB uncompressed JSON; 17,441,561 raw events / 1,181.71 MB in the 55-day evaluation snapshot; 14,398,713 raw events / 977.74 MB in the 46-day scaling slice). Three production data-hygiene problems were solved during ingestion: (1) Multi-Member Truncated Gzip Recovery: an interrupted collector run on 2026-10-27 produced a concatenated multi-member gzip file whose first deflate stream lacked an 8-byte trailer (`zlib.error: Error -3`); our byte-level \x1f\x8b\x08 header scanner (iter_recoverable_gz_lines using zlib.decompressobj(16 + MAX_WBITS)) salvaged all 269,017 rows with zero data loss; (2) Noise Filtering & Global Deduplication: dropped 8,680,821 (40.46%) type == 'categorize' maintenance events and deduplicated day-boundary rcid overlaps, retaining 100.0% (12,773,366 / 12,773,366 in 67d; 10,190,119 / 10,190,119 in 55d) of valid edit, new, and log events; and (3) Missing SSE page_id & macOS Icon\r Protection: deterministic negative 64-bit CRC32 title hashes (title_page_id) prevent live titled edits without numeric IDs from colliding or dropping, while /tmp-staged Parquet writes and pathGlobFilter="*.parquet" eliminate macOS desktop Icon\r commit races.

2.3 Big Data Platforms Used

  • Apache Kafka 3.9.1 (KRaft Mode) & Confluent C Client (confluent-kafka 2.16.1): Runs ZooKeeper-free (KAFKA_PROCESS_ROLES=broker,controller) hosting 3-partition topics wiki.raw.edits and wiki.shift.candidates with idempotent Snappy producers (enable.idempotence=True, acks=all) and an atomic file-spool fallback (FileStreamProducer) for Docker-free execution.
  • Apache Spark 4.2.0 (pyspark.sql.DataFrame & Structured Streaming on OpenJDK 17): Catalyst SQL DataFrames power 100% of production batch curation, zero-inclusive baseline aggregation, watermarked streaming windows (spark-sql-kafka-0-10_2.13:4.2.0), and anomaly scoring. Python RDDs (df.rdd.map / reduceByKey) are used strictly in Experiment #3 for engine comparison.
  • Apache Spark ML (pyspark.ml 4.2.0), Apache Parquet (Snappy), PyArrow 26.0 & Dash 4.5 / Plotly 7.1: Distributed DataFrame ML pipelines (VectorAssembler, StandardScaler, KMeans, RandomForestClassifier), partition-prunable columnar storage, zero-copy Arrow transfers, and an 8-screen Flask/Dash UI supervised by src/run_local.py.

2.4 Statistical Baseline & Machine Learning Methods Used

1. Zero-Inclusive Historical Baselines & Rewriting Volume Decomposition: Averaging only over active hours introduces severe survivorship bias on quiet pages. WikiPulse computes exact zero-inclusive population moments over all D = 47 baseline days and H = 47 × 24 = 1,128 UTC hours without materializing a dense 3.31M × 1,128 grid, alongside session-clustered editor scaling (1/18 of daily distinct editors for 5m windows; 1/6 for 1h windows) and Rewriting Volume decomposition:

μhour = (∑h ∈ active xh) / H,     σhour = √max(σmin2, (∑h ∈ active xh2) / H − μhour2),     Rewriting Volume = ∑ |Δi| − |∑ Δi|

2. Three-Paradigm Anomaly Scoring & Two-Stage Hybrid Spark ML (pyspark.ml) Pipeline: Every window is scored by three detectors simultaneously:

  • Detector A (Fixed Threshold Rule): Flags mainspace (ns=0) windows with ≥ 6 human edits & ≥ 3 editors in 5m (or ≥ 15 edits & ≥ 4 editors in 1h).
  • Detector B (Explainable Historical Score 0–100): Computes Score = wdamp · (Svelocity(35) + Seditors(25) + Schurn(20) + Sconsensus/dispute(10) + Spageviews(10)), where wdamp = 0 for bot-only windows and 0.55 when velocity_zscore < 2.5 (suppressing routine hyperactive-page chatter). Applying wdamp directly to each component guarantees exact additive parity (∑ feature_contributions ≡ historical_score). Disambiguates alerts into CONFIRMED_NEWS (≥ 2.5× baseline pageviews and ≥ 3 editors), BREAKING_NEWS_CANDIDATE, EDIT_WAR_CONTROVERSY (revert_ratio ≥ 0.30 or heavy revert rewriting), and MAJOR_REWRITE (≤ 2 editors moving ≥ 3,500 gross bytes).
  • Detector C (Two-Stage Hybrid Spark ML Pipeline): Stage 1 (Unsupervised KMeans k=6): Standardizes 8 log-stabilized behavioral features (f_edits_human, f_distinct_editors, f_velocity_z, f_editor_surge, f_log_gross_bytes, f_log_rewriting_bytes, f_revert_ratio, f_bot_ratio) via VectorAssembler → StandardScaler(withMean=True, withStd=True) → KMeans(k=6, seed=42) (Silhouette = 0.5546 across 236,074 eval windows; scaled up to 1,078,444 full-lake windows). Discovers 6 editing archetypes (Normal Quiet Baseline 52.48%, Single-Editor Major Rewrite 22.32%, Multi-Editor Edit War 10.50%, Multi-Editor Collaborative Surge 6.44%, Solo Revert/Cleanup 4.35%, Bot-Assisted Maintenance 3.91%) and computes Euclidean distance dcentroid from the normal baseline centroid. Stage 2 (Supervised RandomForestClassifier numTrees=40, maxDepth=7): Appends f_centroid_distance as a 9th feature into a 40-tree Random Forest (top importances: f_distinct_editors = 0.2958, f_edits_human = 0.2461, f_editor_surge = 0.2140, f_log_gross_bytes = 0.0798, f_centroid_distance = 0.0724), blending 0.45 · Skmeans + 0.55 · SRF into spark_ml_score.
  • Wikimedia Lift Wing Gradient-Boosted Revert Risk + 48h Calibration: Pre-filters 75.40% (5,828,465 / 7,729,950) of routine mainspace edits in Spark before scoring candidate revisions via Lift Wing (revertrisk-language-agnostic:predict), combining ML probability with domain heuristics (composite_risk) and matching against actual 48-hour revert outcomes.

3. Evaluation: Experiment Design, Scalability/Performance Metrics, Feature Metrics, Plots and Analysis

3.1 Experiment Design (6 Proposal Experiments)

We executed all 6 proposed experiments: Exp #1 (Manual Sample Audit & Replay Idempotency) audited Spark against a 2,000-event pure-Python reference (rc_2026-09-16.jsonl.gz) and replayed 2026-10-15 (182,521 events) with 30% duplicate injection; Exp #2 (Detector Comparison & Synthetic Injection) evaluated Detectors A, B, and C across 5 injected shift patterns + 2 negative controls, the 8-day post-baseline evaluation horizon (174,468 windows → 1,321 alerts), and a reviewed 200-window sample; Exp #3 (DataFrame vs. RDD) benchmarked 7-day mainspace churn aggregation (747,156 edits); Exp #4 (Scaling & Shuffle Suite) varied worker cores (local[1..6]), weak-scaling slices (4d/core from 4d@1c to 24d@6c), shuffle partitions (4..128), and input horizons (1d..46d / 8.43M rows); Exp #5 (Streaming Load & Outage Recovery) tested 1x..100x replay speeds and a mid-day stop/restart with a 123,537-event backlog; and Exp #6 (Storage & Query Latency) compared raw .jsonl.gz scans against stored Parquet across all dashboard views.

4.2 Key Engineering Takeaways & Operational Lessons

  • Zero-Inclusive Baselines Are Critical for Power-Law Streams: Because 92.31% of Wikipedia articles are normally quiet (< 0.2 edits/day) while 0.084% are chronically hyperactive (≥ 15 edits/day), zero-inclusive sufficient statistics (μ, σ across all 1,128 UTC hours) and session-clustered editor window scaling (1/18 for 5m, 1/6 for 1h) are essential to achieve both 100% recall on emerging quiet-page shifts and low false-alert rates on hyperactive pages.
  • Explainable Additive Scoring and Spark ML Are Complementary: Detector B's exact additive decomposition (∑ feature_contributions ≡ historical_score) gives analysts immediate transparency into why an alert fired, while Detector C's two-stage pyspark.ml pipeline (KMeans centroid distance + RandomForestClassifier) provides a 100.0% precision behavioral filter.
  • Selective Spark Pre-Filtering & Local SHA-256 Caching Enable Sub-Second Enrichment: Filtering out 75.40% of routine mainspace edits in Spark before invoking Wikimedia Lift Wing and caching MediaWiki/Wikidata responses on disk allow rich graph, diff, spatial, and revert-risk context to be served in < 1.35s.

4.3 Future Extensions

  1. Cross-Lingual & Multi-Wiki Federation (wikidatawiki + Top 20 Language Editions): Extending Kafka topic partitioning and RAW_EDIT_SCHEMA keys by (wiki, pageid) to correlate edits across language editions via shared Wikidata QIDs—detecting regional events that break on non-English Wikipedias (e.g., eswiki, jawiki, hiwiki) before propagating to enwiki.
  2. Multi-Hop Streaming Graph Propagation (GraphFrames / PageRank Centrality): Expanding the 1-hop link/backlink spillover graph into a 2-hop streaming neighborhood propagation model to track topic cascades across whole categories in real time.
  3. Semantic Diff Embeddings & Citation Verification: Applying lightweight transformer embeddings and Wikimedia's reference-need / peacock-language Lift Wing models over sanitized diff_snippet text to distinguish sourced factual updates from subtle promotional bias.
  4. Adaptive EWMA Rolling Baselines in Stateful Streaming: Supplementing the 47-day batch baseline table with an exponentially weighted moving average (EWMA) state store in Spark Structured Streaming so long-running seasonal events (e.g., tournaments or election cycles) adapt their (μt, σt) dynamically without batch rebuilds.
